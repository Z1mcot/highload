# Архитектура Rust-решения — DDIA HW2

## 1. Цель и границы

Создать **не HTTP-клиент**, а учебную библиотеку, которая реализует стратегии устойчивости поверх абстрактной отправки подзапроса. Источник требований: `ITMO-DDIA-2026-MSE_MHS-HW-2.md`. Полный набор: default, retries, exponential backoff retries, round-robin, hedging, circuit breaking. Основная цель: понятный человеку код с расширяемыми интерфейсами и тестами.

## 2. Выбранные технологии

- Один crate типа `lib`; без микросервисов, протокола HTTP, отдельного сервера и сложного Cargo workspace.
- Асинхронное выполнение с `tokio`: `time::timeout_at`, `Instant`, `sleep_until`, `select!`, `tokio::test`.
- `async-trait` обеспечивает объектно-безопасный API `&dyn SubrequestSender` / `Arc<dyn SubrequestSender>` без generics в публичных клиентах.
- Hedging хранит futures внутри вызова. Один `std::future::poll_fn` опрашивает их, включая первый опрос всех sender при fanout; дополнительные зависимости и фоновые задачи не нужны.
- Тестовый transport управляется очередью заранее заданных исходов и временем задержки; сетевого вызова нет.

## 4. Минимальные смысловые интерфейсы

Ниже приведена иллюстрация API: детали, необходимые для компиляции, можно уточнять при реализации, сохраняя сами понятия.

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Response {
    pub body: Vec<u8>,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum ServerOutcome {
    Success(Response), // 2xx
    ClientError,       // 4xx
    ServerError,       // 5xx
}

#[async_trait::async_trait]
pub trait SubrequestSender: Send + Sync {
    async fn send(&self) -> ServerOutcome;
}
```

`Timeout` — это исход, который **наблюдает клиент**: фреймворк формирует его, когда истекает deadline отдельной попытки. В тестах зависший сервис моделируется через `pending()`, а не мгновенным возвратом искусственного timeout. Внутри такой исход представлен как `AttemptOutcome::Failure(FailureKind::Timeout)` и отличается от `DeadlineExceeded`. Интерфейс sender намеренно не принимает ни таймауты, ни сценарии ошибок.

`Client::new(latency, SingleStrategy)` и `MultiClient::new(latency, MultiStrategy)` проверяют неизменяемую конфигурацию. `Client::execute(&self, sender)` и `MultiClient::execute(&mut self, senders)` получают объекты sender для одного логического запроса, как и требуется в задании. Состояние маршрутизации мультиклиента хранится отдельно от этих объектов. Возможные ошибки: `AttemptFailed`, `DeadlineExceeded`, `BudgetExhausted`, `NoSenders`, `NoAvailableSenders` и `InvalidConfiguration`. Ошибки выполнения содержат локальную для запроса статистику `RequestStats`: число стартовавших попыток и отдельные счётчики 4xx, 5xx и per-attempt timeout. При успехе возвращается исходный `Response`.

## 5. Бюджеты и таймеры

```rust
pub struct RetryBudget {
    pub max_attempts: usize,
    pub max_client_errors: usize,
    pub max_server_errors: usize,
    pub max_timeouts: usize,
}

pub struct LatencyBudget {
    pub overall: Duration,
    pub per_attempt: Duration,
}
```

Проверяются условия `max_attempts >= 1` и положительность длительностей. **Это принятое здесь толкование, а не дословное определение из задания**: `max_attempts` — общее число запущенных подзапросов (в задании единственная попытка default обозначена как `max_retries=1`). Лимиты для отдельных типов ошибок задают, сколько таких исходов можно получить, прежде чем **следующие попытки будут запрещены**. При лимите 0 операция завершается после первой ошибки этой категории. Сама ошибка при этом учитывается в общем числе запущенных попыток. Граничные случаи нужно проверять отдельно.

Для общего deadline используется `tokio::time::Instant`; оставшееся время вычисляется перед каждой попыткой и паузой. На подзапрос отводится `min(per_attempt, remaining)`. При повторе общий deadline не запускается заново. Если он истекает во время попытки, это нужно отличать от обычного per-attempt timeout, чтобы стратегия не запускала следующий подзапрос. На точной границе времени истёкший deadline важнее уже готового ответа; общий deadline важнее deadline отдельной попытки. Проверка сложения с часами позволяет отклонить слишком большой общий бюджет без panic.

**Политика для 4xx**: задание явно предусматривает fast errors budget для retries, поэтому после 4xx повтор разрешён, пока позволяют этот и остальные бюджеты. При этом **backoff после 4xx не применяется**. Это решение принято для данного задания и не является общей рекомендацией по поведению HTTP-клиента.

## 6. Общий механизм выполнения

`run_subrequest(sender, deadline, per_attempt)` выполняет одну попытку и возвращает `Success | Failure(ClientError | ServerError | Timeout) | DeadlineExceeded`. Учёт попыток ведёт стратегия, а не sender. `execute_sequential` — единственный последовательный цикл попыток; он принимает `Routing` и `SingleStrategy`. Default делает одну попытку, retry использует заданные лимиты, а backoff дополнительно получает необязательный `BackoffSchedule`. Выбор маршрута и обновление состояния здоровья выполняются синхронно; `await` нужен только для отправки и ожидания. Между повторами цикл уступает управление, чтобы runtime мог выполнять другие задачи и обработать отмену со стороны вызывающего кода, даже если ошибки возвращаются сразу.

Формула backoff: `min(max_delay, initial_delay * 2^k)`, где для первой паузы после 5xx/timeout `k=0`. Насыщенная арифметика длительностей ограничивает рост. После 4xx следующая попытка запускается без дополнительной паузы, но показатель степени не сбрасывается. Нельзя спать дольше общего deadline или после исчерпания бюджета. Jitter не используется.

## 7. Стратегии мультиклиента

**Round-robin:** `MultiClient` хранит курсор следующего индекса между вызовами. `Routing` выбирает sender по формуле `cursor % len` и сдвигает курсор **при старте каждого подзапроса**. `MultiStrategy::RoundRobin(SingleStrategy)` можно сочетать с default, retry или backoff; общий цикл выбирает sender перед каждой попыткой. Новый клиент намеренно начинает с нового курсора и пустой истории breaker.

**Hedging:** первый sender запускается сразу. Если к моменту `hedging_delay` не пришёл **ни один ответ**, остальные sender запускаются одновременно, каждый не более одного раза. Если первый sender вернул любой ответ, включая 4xx/5xx, fanout не выполняется. Если успешного ответа нет, запрос остаётся в ожидании до общего deadline, даже если все sender уже завершились ошибкой. Учитывается только **общий** latency budget, а не лимиты на попытку или категории ошибок. Каждый вызов повторно использует `run_subrequest` с оставшимся общим временем. На границе fanout сначала проверяется, не готов ли ответ; затем учитывается задержка. Приоритет выше всего у общего deadline. Нулевая задержка допустима. Futures закрепляются в памяти и опрашиваются локально; при fanout запускаются все оставшиеся sender, даже если одна из дополнительных попыток сразу успешна. При возврате из вызова или удалении его future все незавершённые futures синхронно удаляются. Если одновременно готовы несколько успешных ответов, выбирается первый по порядку sender в списке. Фоновые задачи не создаются.

**Circuit breaker:** история для каждой позиции хранится в `MultiClient` между логическими запросами. Когда накоплено полное окно из `N` завершённых подзапросов, доля ошибок `> threshold` открывает breaker этого sender на время `T`. Ошибками считаются 4xx, 5xx и timeout. Запущенная попытка, остановленная общим deadline, тоже считается ошибкой для оценки здоровья, но не увеличивает per-attempt timeout в `RequestStats`. Отмена со стороны вызывающего кода не добавляет завершённый исход. После окончания cooldown разрешается **одна проба** (`HalfOpen`): успех закрывает breaker и очищает окно, ошибка открывает его снова на время `T`. Если проба была отменена, sender снова может участвовать в следующем вызове. Состояния заданы явно: `Closed | Open(until) | HalfOpen`; если cooldown выходит за пределы диапазона часов, sender остаётся изолированным. Открытые sender пропускаются при обходе round-robin; если доступных нет, сразу возвращается `NoAvailableSenders`. Метод `execute(&mut self, ...)` допускает только один вызов за раз, поэтому параллельных проб и блокировок через `await` не возникает. Число sender и соответствие их позициям должны оставаться постоянными между вызовами. Изменение числа отклоняется без сброса истории, а за неизменность идентичности серверов отвечает вызывающий код. У независимых мультиклиентов независимое состояние.

## 8. Что задано явно, а что выбрано при проектировании

| Тема | Указано в задании | Принятое в проекте решение, которое нужно документировать |
|---|---|---|
| Sender | Объект используется для одного логического запроса и обслуживает серию подзапросов | `execute` получает объекты, область жизни которых ограничена запросом; состояние маршрутизации хранит клиент |
| Default | Ровно один подзапрос; latency timeout | Соглашение об имени `max_attempts=1` |
| Retries | Последовательные повторы до успеха или исчерпания бюджета | Ошибки учитываются по фактически полученным исходам и запрещают последующие попытки при достижении лимита |
| Backoff | Только после 5xx или timeout | Начальная задержка, множитель 2 и необязательный верхний предел |
| Round-robin | Каждый следующий **подзапрос** отправляется следующему sender | Постоянный курсор клиента; общий retry-цикл выбирает sender перед каждой попыткой |
| Hedging | Остальные sender запускаются после задержки; нужен первый успех; ошибка при исчерпании общего latency budget | Ранние ответы не 2xx не завершают запрос |
| Breaker | Round-robin и любой разумный breaker; приведены два примера | Полное скользящее окно, строгий порог, cooldown, состояние HalfOpen, немедленная ошибка, если все sender открыты, последовательный API с изменяемым клиентом |

## 9. План тестирования

Тесты находятся в шести integration-файлах. Управляемый fake записывает индекс sender, время старта, завершённые и активные вызовы, а также отмены. Зависания моделируются future, который никогда не завершается. В тестах времени используются `#[tokio::test(start_paused = true)]` и `advance`, без сети и ожиданий по реальным часам. Проверяются все категории бюджетов со значениями 0/1/2, общие deadline, интервалы и верхняя граница backoff, композиция round-robin, гонки на границе hedging и очистка проигравших, а также восстановление breaker и отмена между несколькими запросами. В README показано, как требования связаны с реализацией и тестами.
